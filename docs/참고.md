# 1. 용어집


> 구현 문서가 아님. 기획 대화에서 헷갈리기 쉬운 말만 정리.

| 용어 | 쉬운 말 |
|------|---------|
| **로온드** | 「이 지역, 지금 뭐가 있지?」 앱. Local On |
| **기회 (Opportunity)** | 앱에 올리는 한 건의 카드 (모집·축제·장소·혜택 등) |
| **NOW** | 메인에서 「지금/곧」 영역 |
| **APPLY** | **지금 신청할 수 있어요** — 접수·신청이 필요한 기회 |
| **ENJOY** | **곧 열리는 기회** — 축제·공연 등 가서 즐기는 것 |
| **ANYTIME / DISCOVER** | **언제든** — 관광지·맛집 등 상시 발견 |
| **MY CHANCE / BENEFIT** | **나에게 해당** — 조건형 혜택 (MVP는 거의 안 넣음) |
| **MVP** | 첫 출시에 넣는 최소 범위 |
| **화이트리스트** | APPLY로 **허용할** 공고 종류 목록 |
| **블랙리스트** | 자동으로 버리는 공고 (채용·입찰 등) |
| **pending_review** | 자동으로 후보만 잡아 두고, 사람이 승인해 공개하기 전 상태 |
| **published** | 앱에 노출되는 상태 |
| **applicationEnd** | 신청 마감일 (없으면 앱에 올리지 않음) |
| **원문 CTR** | 상세에서 「공식 원문 보기」를 누른 비율 — 핵심 성공 지표 |
| **스파이크** | 본개발 전에 짧게 해 보는 실험 (예: 공고 90일) |
| **스캐폴딩** | 앱 코드 뼈대 만들기 → **지금은 하지 않음** (기획 후·구현 계획 후) |
| **Phase A** | 구현 단계 중 앞부분 이름 (샘플 데이터로 화면) — 아직 착수 안 함 |

## 작업 순서 (합의)

1. **기획서 보완·확정** ← 지금 여기
2. **구현 계획서** (할 일 쪼개기, 일정·의존성)
3. **구현** (코드·스캐폴딩)

## 1. 수집 개요

| 항목 | 값 |

### 수집 제약 (정직 기록)

- 연구 박스에서 **HTTPS TLS handshake EOF** (`curl: (35)`) 발생 → **HTTP**로 동일 목록/상세 수집 성공.
- UI 날짜 필터 미사용. 90일 경계까지 페이지를 이어가며, 창 밖 비율이 과반이 되는 시점에서 중단 (`majority_outside_page_13`).
- 창 내 583건은 90일 컷오프를 충족. (전체 스크랩 650건 중 일부는 컷오프 이전)

## 2. 키워드 후보 분류

**POSITIVE**: 모집, 참가, 신청, 체험, 관광, 체류, 한달, 시민, 교육, 공모, 지원사업, 프로그램 참가, 선착순, 모집공고  
**NEGATIVE**: 입찰, 용역, 공시송달, 고시, 과태료, 도시계획, 실시계획, 낙찰, 수의계약, 보상, 수용, 개찰, 견적  

규칙: `score = pos_hits - neg_hits`, 강네거티브(입찰·용역·공시송달 등) 있으면 제외, `score≥1` 또는 시민 모집 패턴이면 후보.

| 항목 | 값 |
|------|-----|
| 후보 건수 | **105건** |
| 후보율 | **18.0%** (105/583) |
| 후보 중 ‘선정결과’성 | 4건 (소수) |
| 후보 중 모집·신청형 | 92건 |

## 3. 샘플 라벨 · Precision / Recall

- 층화 유사 샘플 **50건** (후보 25 + 비후보 25), Loond 시민 APPLY 관점 휴리스틱 라벨 (`true_APPLY_opportunity`).
- 제외 취지: B2B 여행사 모집, 용역/입찰, 순수 행정 공시송달 등.
- 경계 사례: 통장·위원 공개모집·기간제 채용·공람공고 등은 라벨러 판단에 따라 FP/TP 혼재 가능 → 아래 수치는 **상한에 가까운 추정**.

| 지표 | 샘플(50) | 창 전체 휴리스틱(참고) |
|------|----------|------------------------|
| TP / FP / FN / TN | 21 / 4 / 0 / 25 | TP 85 / FP 20 / FN 1 |
| **Precision** | **84%** (21/25) | ≈81% |
| **Recall (추정)** | **100%** (FN=0 in sample) | ≈99% (비후보 전수 스캔 FN≈1) |

해석: 키워드 1차 필터는 **시민 모집·수강·지원사업**을 잘 걸러내지만, 샘플 FP 예시는 기간제 채용·정비 공모·공람·지원사업(대출이자) 등 **APPLY 제품 적합도가 낮은 행정/채용성** 문서.

## 4. 상세 페이지 · applicationEnd 추출

후보 상세 **10건** HTTP 조회 (공손히 페이지 간 지연).

| 항목 | 값 |
|------|-----|
| 상세 fetch 성공 | 10/10 |
| HTML에서 **게재기간 종료일** proxy 추출 | **90%** (9/10) |
| HTML에서 **진성 신청마감(applicationEnd)** | **≈0%** (본문에 신청/접수 마감 필드 없음) |
| HWP/HWPX 첨부 존재 | **8/10** |
| HWP만 있고 날짜 실패 | 1/10 (결과 공고성) |

**핵심**: 상세 HTML은 목록과 동일한 메타(게재일자·게재기간·첨부) 위주이며, **실제 모집 일정은 HWP 본문에 있는 경우가 대부분**. 게재기간 종료일을 applicationEnd 대용으로 쓸 수는 있으나 오탐·과대 기간 위험.

## 6. 결론 (A/B/C)

**선택: (B) 검증 비중 상향**

근거 요약:

1. **목록 키워드 필터는 유효** — 샘플 precision ≈ **84%**, 후보율 ≈ **18%**로 노이즈(공시송달·과태료 등) 대량 배제 가능.  
2. 그러나 **제품 적합 APPLY만 자동 확정하기엔 부족** — FP에 채용·공람·결과공고 혼입, Loond 관광/체류 축과 무관한 수강·위원 모집이 후보 다수.  
3. **마감일 자동 완결 불가** — 진성 applicationEnd HTML 추출 ≈0%, HWP 파싱 또는 게재기간 proxy+사람 확인 필요 → (A) 80–90% 자동+가벼운 검증 OK에는 미달.  
4. 후보가 창 내 100건+ 규모로 상시 나오므로 **완전 시즌 수동 큐레이션(C)만**으로 두기엔 기회 손실·반복비용이 큼.

→ **자동 후보화 + 운영자 검증 큐(비중 상향)** 가 현실적.

## A. 초기 기획 검토

# 로온드 기획 v0.1 검토 메모

검토일: 2026-09-14

## 총평

방향이 선명하다. 「지역정보 앱」이 아니라 「기회 발견」으로 포지션을 잡은 점이 가장 강하다. MVP를 수원 1곳으로 제한한 것도 현실적이다. 다음으로 **데이터 설계 표**로 가는 판단에 동의한다.

## 잘 잡힌 것

1. 한 줄 UX ("이 지역, 지금 뭐가 있지?")가 의사결정 기준이 된다.
2. APPLY / ENJOY / DISCOVER / BENEFIT 분류가 수집·화면·필터를 관통한다.
3. 메인 UI를 카테고리가 아니라 시간·행동 섹션으로 둔 것.
4. 회원가입 제거, 입력 최소화.
5. 지자체 공고를 「자동 후보 + 검증」으로 정의한 것.
6. 핵심 지표를 클릭·재방문으로 둔 것.

## 보완이 필요한 곳

### A. Opportunity vs 상시 정보

DISCOVER(화성, 맛집)는 「지금」이 약한 상시 정보다. 메인에서 APPLY/ENJOY를 위에 두고 DISCOVER는 「언제든」/탐색 탭으로 분리하면 「지금」 포지션이 흐려지지 않는다.

### B. status 상태머신

스키마에 status만 있고 값이 없다. 최소안:

- draft / pending_review / published / expired / rejected
- 노출 조건: published AND (endDate 또는 applicationEnd가 미래이거나 null인 상시)

### C. 「이번 달」의 정의

메인 카피가 「이번 달」인데, APPLY는 신청 마감 임박, ENJOY는 개최일, BENEFIT는 상시일 수 있다. 섹션별 정렬 규칙을 문서화할 것. 예:

- APPLY: applicationEnd 가까운 순, 아직 신청 가능만
- ENJOY: startDate가 앞으로 30일 이내
- DISCOVER: 인기/큐레이션 (시간 비의존)
- BENEFIT: 프로필 매칭 점수순 (없으면 숨기거나 「조건 입력」 CTA)

### D. category vs type

둘 다 있으면 중복된다. type=4종 고정, category는 출처/세부분류(축제·공연·한달살기…)로 역할을 나누자.

### E. 법적·운영 리스크 (MVP에도 한 줄)

- 공공 API 이용약관·출처 표기 (sourceName/sourceUrl로 대응)
- 공고 자동 요약의 오류 책임 → pending_review 또는 「원문 확인」강조
- 개인화 입력은 기기 로컬 저장 명시 (회원가입 없어도 개인정보 이슈 가능)

### F. BENEFIT MVP 범위

「기본적인 개인 혜택」이 모호하다. 수원 MVP에서는 TourAPI+문화+지자체 APPLY/ENJOY만 넣고, BENEFIT는 프로필 CTA만 두거나 수동 시드 3~5개로 제한하는 편이 안전하다.

### G. 기술 스택 미정

기획은 데이터·제품 중심이라 OK. 다만 다음 문서에서 앱(Flutter 등) / 수집 워커 / DB를 한 줄이라도 적어 두면 개발 착수가 빨라진다.

## 우선순위 제안

1. 수원 데이터 설계 표 (합의된 다음 단계) — 최우선
2. Opportunity 상태·정렬 규칙 1페이지
3. 메인 와이어 고정 (섹션 4개)
4. 그다음 스캐폴딩

## 결론

v0.1은 **출시 가능한 제품 기획의 뼈대로 통과**해도 된다. 막히는 지점은 UI가 아니라 「빨간 영역(지자체 공고) 자동화」이며, 수원 데이터 표가 그 답을 구체화한다.
