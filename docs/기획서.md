## 1. 한 줄 정의

로온드는 **선택한 지역에서 지금 이용할 수 있는 기회**를 찾아주는 앱이다.

- 핵심 UX: **"이 지역, 지금 뭐가 있지?"**
- 이름 배경으로 *Local On*을 참고할 수 있으나, **공식 어원처럼 고정하지 않는다.** (브랜드 설명은 `참고.md`)
- 철학: 정보를 많이 보여주는 앱이 아니라, **놓치고 있던 지역의 기회를 발견**하게 하는 앱.

### 기존 앱과의 차이

| 유형 | 메시지 |
|------|--------|
| 관광 앱 | 이런 관광지가 있습니다 |
| 축제 앱 | 이번 주 축제가 있습니다 |
| 지원 앱 | 이런 지원금이 있습니다 |
| **로온드** | **이 지역에서 지금 이런 기회가 있습니다** |

## 2. 정보 구조

```
NOW = Opportunity          ANYTIME = Discovery       MY CHANCE
├─ APPLY  지금 신청         └─ DISCOVER 가볼 곳/맛집    └─ BENEFIT (얇게)
└─ ENJOY  곧 열림
```

| 축 | type | MVP |
|----|------|-----|
| NOW | APPLY, ENJOY | **핵심** |
| ANYTIME | DISCOVER | 보조 |
| MY CHANCE | BENEFIT | **CTA만** (시드 콘텐츠도 MVP에서 생략 가능) |

- **type** = 사용자 행동 (APPLY / ENJOY / DISCOVER / BENEFIT)
- **category** = 콘텐츠 성격 (수강, 축제, 관광…)

## 3. 누구를 위한 앱인가

**A. 우리 동네 뭘 놓쳤지?** — 수원 거주/생활, 공고를 안 찾아봄, 신청·행사만 훑고 원문으로 이동  
**B. 이번 주말 수원에서** — 나들이, ENJOY/DISCOVER 위주, 체험 신청이 있으면 관심  

아닌 사람: 채용 구직, 입찰 업체, 보조금 헤비유저(후순위)

### 성공 지표

| 구분 | 지표 |
|------|------|
| **North Star** | 상세 → **공식 원문 보기** 클릭률 (Outbound CTR) |
| 보조 | 카드→상세 클릭률, 주간 재방문, APPLY 빈 날(폴백 비율) |
| 수익 | AdMob eCPM/노출 — North Star를 해치지 않는지 |

실패 신호: 원문 안 누르고 광고만 / NOW 자주 빔 / “관광앱이랑 뭐가 다르지?”

## 4. 메인 UX

### NOW
- 🔥 지금 신청할 수 있어요 (APPLY)
- 🎉 곧 열리는 기회 (ENJOY)

### ANYTIME
- 가볼 만한 곳 / 지역에서 발견한 곳 (DISCOVER)

### MY CHANCE
- 조건 매칭 시에만. 없으면 섹션 숨김 또는 CTA만

### APPLY가 적을 때 (폴백 — 확정)
- APPLY와 ENJOY **섹션은 항상 분리**한다. ENJOY를 APPLY 칸에 섞어 넣지 않는다.
- APPLY가 0~2건이어도 섹션은 유지하고, 부족하면 솔직한 Empty:
  - 0건: *「지금 신청할 수 있는 기회가 없어요.」*
  - 1~2건: 있는 것만 보여 줌 (억지 채움 없음)
- ENJOY는 아래에서 독립적으로 *「이번 주에 열려요」* 등으로 살린다.
- (폐기) APPLY&lt;3일 때 ENJOY를 NOW 상단 APPLY처럼 피처링하던 방식 — **신뢰성 때문에 폐기**


### 온보딩
- 필수: 지역(MVP는 수원 고정 가능)
- 선택 프로필 입력은 MVP에서 생략 가능 (BENEFIT은 CTA만)
- **회원가입 없음**

### 화면 (최소)
메인 · 상세 · Empty/Error · 설정

### 상세
- 요약, D-Day, 출처  
- Primary CTA: `[🔗 {sourceName} 공식 원문 보기]`  
- 안내: 공식 사이트에서 첨부(HWP/PDF) 확인이 필요할 수 있음  
- AI/요약은 원문 없이 지어내지 않음

## 6. 데이터 모델

### Opportunity 필드
id, region, title, type, category, summary, description,  
startDate/endDate, applicationStart/applicationEnd,  
target, benefit, location, organization, thumbnail,  
**sourceName, sourceUrl, sourcePublishedAt**(필수),  
status, opportunityScore, createdAt, updatedAt

### status
`draft → pending_review → published → expired`  
실패 시 `rejected` / 보관 `archived`

### 자동 만료
- APPLY/BENEFIT: `now > applicationEnd` → expired  
- ENJOY: `now > endDate` → expired  
- DISCOVER 상시: endDate null 허용

### applicationEnd Fallback (필수)
파싱 실패·불확실 → `applicationEnd=null` + **`pending_review` only**. published 금지.  
(상시/예산 소진 시까지도 확신 없으면 review)

### 검증 체크리스트 (pending_review → published)

운영자가 확인하는 항목을 고정한다. 맘대로 큐레이션이 아니라 **동일 데이터 처리**:

- [ ] 로온드 APPLY(화이트리스트)에 적합한가?
- [ ] 지금 신청·접수 가능한 공고인가? (결과/종료 아님)
- [ ] 신청 마감일(`applicationEnd`) 확인·입력했는가? (**없으면 published 금지**)
- [ ] 행사/프로그램 기간 확인했는가?
- [ ] 대상 확인했는가?
- [ ] 지원·혜택 내용 확인했는가?
- [ ] 공식 원문 URL 정상인가?
- [ ] 제목/요약이 원문과 어긋나지 않는가?

### 정렬
1. **Hard Sort** (섹션 규칙)  
   - APPLY: 신청가능 → 마감임박 → 최신  
   - ENJOY: 오늘 → 7일 → 30일  
   - BENEFIT: 매칭 → 마감 → 최신  
2. 동점에만 `opportunityScore`

### Opportunity Score
- 구조(가중치)는 **정의만** 해 둔다: 신청가능성 +30 / 마감임박 +20 / 지역연관 +20 / 혜택규모 +0~15 / 희소성 +10 / 최신성 +0~5
- **MVP 구현 후순위.** Hard Sort가 실제 순서를  determin. 클릭 데이터 쌓인 뒤 조정.

### 중복
제목 유사 + 날짜·장소 유사 → TourAPI 우선, 나머지 rejected
