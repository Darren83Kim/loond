---

## 1. 구현 목표

확정된 기획을 **수원 MVP**로 옮긴다.

- 사용자가 수원 NOW에서 APPLY / ENJOY를 보고, 상세에서 **공식 원문**으로 나간다.
- APPLY는 **자동 후보 + 사람 검증**으로 published 된다.
- MVP 저장은 **published JSON (정적)** 으로 최대한 단순하게 (Supabase는 Phase B).

이 문서에서 **새 기능을 발명하지 않는다.** 순서·단위·완료 조건만 정한다.

## 2. 전체 아키텍처 (Phase A)

```text
수원시 공고 / TourAPI / 문화포털
            ↓
     Python Worker
            ↓
   candidate → pending_review
            ↓
     검증 체크리스트 (사람)
            ↓
        published
            ↓
   opportunities.json  (정적 호스팅)
            ↑
        Flutter 앱
            ↓
     AdMob (테스트→실키)
```

| 층 | 기술 | MVP |
|----|------|-----|
| App | Flutter | ✅ |
| Worker | Python + GitHub Actions (일 1회) | ✅ |
| Storage | published JSON 정적 | ✅ Phase A |
| DB/검증 UI | Supabase 등 | ⏳ Phase B (필요 시) |

## 3. Phase / Epic 구조

```text
[기획 완료]
     ↓
EPIC 1  수원 APPLY 파이프라인 PoC   ← 가장 먼저 (데이터 증명)
     ↓
EPIC 2  정적 데이터 계약·저장
     ↓
EPIC 3  Flutter MVP 화면
     ↓
EPIC 4  ENJOY / DISCOVER 수집
     ↓
EPIC 5  운영 자동화 (스케줄·알림)
     ↓
EPIC 6  AdMob
     ↓
EPIC 7  테스트 / 출시
```

**원칙:** EPIC 1이 실패하면 Flutter를 깊게 파지 않고 파이프라인을 다시 잡는다.  
EPIC 1이 성공하면 앱 작업은 상대적으로 평범해진다.

## EPIC 1. 수원 APPLY 파이프라인 PoC

**목적:** “공고 → 검증 가능한 Opportunity”가 **실제로** 나오는지 증명.

| ID | Task | 내용 |
|----|------|------|
| 1-1 | 지역 코드 상수 | `region_id=suwon`, `region_name=수원`, TourAPI area/sigungu는 조회 후 상수화 |
| 1-2 | 시청 공고 수집 | `BD_ofrList.do` 목록 (제목·부서·게재일·상세 URL) |
| 1-3 | 후보 필터 | 기존 스파이크 키워드 규칙 (pos/neg) |
| 1-4 | 제외 규칙 | 블랙리스트 + APPLY 화이트리스트 불일치 → rejected |
| 1-5 | Opportunity 변환 | 기획서 필드와 1:1 매핑 (status=`pending_review` 기본) |
| 1-6 | HWP/HWPX 처리 | 첨부 존재 여부 기록; **마감일 추출 PoC** (성공률 측정, 실패 시 수동 입력 전제) |
| 1-7 | pending_review 산출 | 검증용 큐 파일/시트 (JSON 또는 CSV) |
| 1-8 | 검증 → published | 기획서 체크리스트로 5~10건 수동 승인 |
| 1-9 | JSON 출력 | published만 `opportunities.json` (또는 `apply_published.json`) |
| 1-10 | 성공 기준 | 아래 DoD |

### EPIC 1 Definition of Done

- [ ] 최근 공고에서 후보를 **자동 추출**한다.
- [ ] 화이트리스트/블랙리스트로 노이즈를 걸러낸다.
- [ ] 검증 대상 **5~10건**에 대해 `applicationEnd`를 **확인·기입**한다 (자동 실패 시 수동 OK).
- [ ] 유효 published Opportunity JSON을 **1개 이상** 생성한다.
- [ ] `applicationEnd` 없는 건은 published에 **절대 안 넣는다**.
- [ ] HWP 한계·수동 검증 비중을 짧은 메모로 남긴다.

**실패 시:** 앱 EPIC을 진행하지 않고, 수집 소스·수동 큐레이션 비중을 재설계.

## 4. 의존성

```text
1-1 → 1-2…1-10 → 2-* → 3-* 
                ↘ 4-* (3과 일부 병렬 가능하나 JSON 계약(2) 이후)
5는 1 안정화 후
6은 3 화면 이후
7은 3+4+6 이후
```

**병렬 가능:** EPIC 3 뼈대 ↔ EPIC 1 PoC (단, 앱은 샘플 JSON으로, 실데이터는 1·2 완료 후 연결)

**권장 실제 순서:** 1 완료 → 2 → 3에 실데이터 연결 → 4 → 5 → 6 → 7

## 9. 착수 전 테크 메모 (기획 결함 아님 · EPIC에서 체크)

### A. TourAPI 수원 지역코드 (EPIC 1-1 / 4-1)
- 경기도 `areaCode`는 통상 **31**.
- 수원은 단일 sigungu가 아니라 **장안·권선·팔달·영통** 등으로 나뉠 수 있음.
- 선택지:
  1) 구별 `sigunguCode` **다중 호출 후 병합**, 또는
  2) `areaCode=31` 조회 후 `addr1` 등에 **「수원」 필터** (호출 수↓, EPIC 1-1에서 실측 후 상수화).

### B. HWP 마감일 · 수동 검증 비용 (EPIC 1-6~1-8)
- HTML에 진성 `applicationEnd`가 거의 없음 → HWP 확인이 기본.
- 예상: 원문 열기 → HWP → 마감 기입 **건당 약 30초~1분**.
- 하루 후보 3~5건이면 **수 분** 수준 → 1인 운영 OK. DoD는 “자동 추출 100%”가 아니라 **확인·기입된 published**.

### C. 정적 JSON 호스팅 (EPIC 2-4 / 5)
- Flutter fetch 시 **CORS**(웹) 및 호스팅 헤더 확인.
- **캐시 버스팅**: `opportunities.json?v={updatedAt 또는 Actions run id}` 권장 (구 JSON 고착 방지).

### D. AdMob 네이티브 레이아웃 (EPIC 6-1)
- 4카드마다 네이티브 노출 시 **Opportunity 카드와 높이·톤을 맞춘 커스텀 템플릿**을 Task에 포함 (플랫폼별 깨짐 방지).
