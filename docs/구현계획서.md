## 1. 구현 목표

확정된 기획을 **수원 MVP**로 옮긴다.

- 사용자가 수원 NOW에서 APPLY / ENJOY를 보고, 상세에서 **공식 원문**으로 나간다.
- APPLY는 **자동 후보 + 사람 검증**으로 published 된다.
- MVP 저장은 **published JSON (정적)** 으로 최대한 단순하게 (Supabase는 Phase B).

이 문서에서 **새 기능을 발명하지 않는다.** 순서·단위·완료 조건만 정한다.

## 2. 전체 아키텍처 (Phase A)

```text
수원시 공고 / TourAPI / 문화포털
            ↓
     Python Worker
            ↓
   candidate → pending_review
            ↓
     검증 체크리스트 (사람)
            ↓
        published
            ↓
   opportunities.json  (정적 호스팅)
            ↑
        Flutter 앱
            ↓
     AdMob (테스트→실키)
```

| 층 | 기술 | MVP |
|----|------|-----|
| App | Flutter | ✅ |
| Worker | Python + GitHub Actions (일 1회) | ✅ |
| Storage | published JSON 정적 | ✅ Phase A |
| DB/검증 UI | Supabase 등 | ⏳ Phase B (필요 시) |

## 9. 착수 전 테크 메모 (기획 결함 아님 · EPIC에서 체크)

### A. TourAPI 수원 지역코드 (EPIC 1-1 / 4-1)
- 경기도 `areaCode`는 통상 **31**.
- 수원은 단일 sigungu가 아니라 **장안·권선·팔달·영통** 등으로 나뉠 수 있음.
- 선택지:
  1) 구별 `sigunguCode` **다중 호출 후 병합**, 또는
  2) `areaCode=31` 조회 후 `addr1` 등에 **「수원」 필터** (호출 수↓, EPIC 1-1에서 실측 후 상수화).

### B. HWP 마감일 · 수동 검증 비용 (EPIC 1-6~1-8)
- HTML에 진성 `applicationEnd`가 거의 없음 → HWP 확인이 기본.
- 예상: 원문 열기 → HWP → 마감 기입 **건당 약 30초~1분**.
- 하루 후보 3~5건이면 **수 분** 수준 → 1인 운영 OK. DoD는 “자동 추출 100%”가 아니라 **확인·기입된 published**.

### C. 정적 JSON 호스팅 (EPIC 2-4 / 5)
- Flutter fetch 시 **CORS**(웹) 및 호스팅 헤더 확인.
- **캐시 버스팅**: `opportunities.json?v={updatedAt 또는 Actions run id}` 권장 (구 JSON 고착 방지).

### D. AdMob 네이티브 레이아웃 (EPIC 6-1)
